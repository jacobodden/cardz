Implementation shape

Both games are the same module with a different win direction. A small factory keeps them in sync:

// src/games/points.ts
function makePointsGame(
  slug: string,
  scoreDirection: 'high' | 'low',
): CardGame {
  return {
    slug,
    scoreDirection,
    roundMode: 'open',
    usesDealer: false,
    getConfigSchema: () => [],
    getRounds: () => [],            // open games create rounds as they go
    getRoundSchema: () => [
      { key: 'points', label: 'Points', type: 'number', scope: 'player' },
    ],
    computeScore: (_meta, inputs) => inputs.map((i) => {
      const points = Number(i.data.points ?? 0)
      return { player_id: i.player_id, score: points, data: { points } }
    }),
  }
}

export const highScore = makePointsGame('high-score', 'high')
export const lowScore  = makePointsGame('low-score',  'low')
No config needed. Open-ended games do not need a round count at setup. The session starts at round 1 and the user decides when to stop.

3Engine & data changes

3.1 Game capability flags

Add three optional capabilities to CardGame so the UI stops hardcoding game slugs:

// src/games/types.ts
export interface CardGame {
  slug: string
  scoreDirection: 'high' | 'low'   // NEW — drives winner + completion copy
  roundMode?: 'fixed' | 'open'     // NEW — defaults to 'fixed'
  usesDealer?: boolean             // NEW — defaults to false
  getRounds(playerCount: number, config?: Record<string, any>): RoundMeta[]
  getRoundSchema(round: RoundMeta): InputField[]
  computeScore(meta: RoundMeta, inputs: PlayerScoreInput[]): PlayerScoreResult[]
  getConfigSchema(): ConfigField[]
}
  • scoreDirection replaces the current slug === 'pay-me' check in findWinners and the completion message.
  • roundMode: 'open' tells session/round logic not to auto-complete and not to pre-generate round_configs.
  • usesDealer stops generic games from showing a meaningless dealer name. Existing games set it explicitly (Up & Down: true).

  // 1. Delete the trailing unscored round (if any).
  // 2. Set session.status = 'completed'.

3.5 Scoreboard query

  • maxRounds becomes Math.max(totalRounds, roundConfigs.length, rounds.length) so open games still build score arrays.
  • Load all scores for the session’s rounds in one query instead of one query per player per round. Open-ended games can grow long, so this keeps the screen fast.

3.6 Seeding for existing installs

seedGames currently returns early when the games table is non-empty, so existing users would never see the new games. Change it to insert only missing slugs:

const existing = await db.games.toArray()
const existingSlugs = new Set(existing.map((g) => g.slug))
const missing = GAME_SEEDS.filter((g) => !existingSlugs.has(g.slug))
if (missing.length) await db.games.bulkAdd(missing)
No Dexie schema bump needed. Win direction and round mode live in the game implementation registry, not in the database. The games table only gains two rows.

4Open-ended round lifecycle

Every open game keeps exactly one unscored “current” round in the database:

  1. Start — round 1 is created with empty data.
  2. Submit — scores are written for the current round, then round N+1 is created automatically.
  3. Finish — the trailing unscored round is deleted and the session is marked completed.
  4. Undo — the last scored round’s scores are deleted, the session reopens, and that round becomes the current round again.
StateRounds in DBSession statusScreen shows
FreshR1 (unscored)activeRound 1 inputs
After 3 submitsR1–R3 scored, R4 unscoredactiveRound 4 inputs, history R1–R3
FinishedR1–R3 scored (R4 deleted)completedWinner banner + final cards
Undo after finishR1–R2 scored, R3 unscoredactiveRound 3 inputs again
Edge case: finishing with zero scored rounds is blocked in the UI. Undo is available after completion so a mis-tap on Finish is recoverable.

5Mobile-first card UI

5.1 Screen anatomy

  1. Session header — title and game name.
  2. Round bar — “Round 7” (or “Round 7 of 11” for fixed games), plus Undo and Finish actions. Fixed games also get a thin progress bar.
  3. Round settings — only when the current round has round-scope fields (e.g. Up & Down trump). Hidden for generic games.
  4. Player cards — one per player in a single column on every screen size, including desktop. The column is width-capped so inputs stay thumb-friendly.
  5. Sticky submit dock — one shared “Submit Round” button that stays reachable while entering scores.

5.2 Player card

  • Name + total — total is the visual anchor (large, bold).
  • This round — the game’s player-scope fields, rendered as large touch targets:
    • Generic points: one number input, inputMode="numeric", no minimum.
    • Up & Down: bid number + made/missed segmented buttons.
    • Pay Me: cards-left number input.
  • Recent rounds — the last two scored rounds as small chips, e.g. R5 5 R6 12.
  • Trump visibility — for Up & Down, every round chip and expanded-history cell carries that round’s suit, e.g. R2 ♥ 12. The old table header showed trump per round; this keeps that information without the wide table.
  • All rounds — expand toggle. Opens a wrapped grid of round chips for that player only. No horizontal scroll.
  • Winner — crown and amber card treatment when the game is complete. During play, the leader gets a subtle “Leading” pill (optional; see visual notes).

5.3 Why this fixes the scrolling problem

Today: every round is a table column. An 11-round game is wider than a phone; a 20-round home game is much worse. The current round inputs also sit below the table, so users scroll sideways and vertically.
Proposed: rounds become per-player history inside a card. The current round is always the input in the card. Only the expanded history grows, and it wraps into rows instead of extending sideways.

5.4 Interaction details

  • Sticky submit: position: sticky; bottom: 0 with a blurred surface, safe-area bottom padding, and the error message above the button. It disappears when the game is complete.
  • Expand state: local to each card. Tapping “All rounds” toggles that player only; other cards stay compact.
  • History order: recent chips read oldest → newest (R5 then R6). Expanded history is chronological (R1 → Rn) so the progression is easy to scan.
  • Input sizing: 44px minimum height, 16px font to prevent iOS zoom-on-focus.
  • Completed state: winner banner (“Game complete — Alice wins!”) plus final cards. Undo remains in the round bar so the game can be reopened.
  • Fixed games: “Round 7 of 11” + progress bar. Open games: “Round 7 · 6 scored”.
  • Empty points: treated as 0 for now, matching existing games. We can decide during visual iteration whether generic points should require an explicit value.

8Testing & design history with Playwright

Playwright gives us two things at once: functional end-to-end coverage of the new game flows, and committed screenshots that act as both a regression guard and a browsable record of the design.

Two layers:
  • Regression baselines — toHaveScreenshot() assertions in tests/visual/. CI fails on an unexpected visual diff.
  • Design history — a dated screenshot gallery in docs/design-history/, captured intentionally at design milestones and committed.

8.1 Setup

  • Add @playwright/test as a dev dependency and install Chromium (npx playwright install --with-deps chromium).
  • Two projects: mobile-chrome (Pixel 7) and desktop-chrome (1280×800). Use deviceScaleFactor: 1 so snapshots stay small and stable.
  • The webServer runs the Vite dev server on 127.0.0.1:4173. The dev base path is / (production uses /cardz/), so baseURL is the root.
  • Set PLAYWRIGHT=1 in the web-server environment and gate the PWA dev service worker with devOptions: { enabled: !process.env.PLAYWRIGHT }. This prevents the service worker from caching assets between test runs.
  • Disable animations in screenshots and allow a small maxDiffPixelRatio for anti-aliasing.
// playwright.config.ts
import { defineConfig, devices } from '@playwright/test'

export default defineConfig({
  testDir: './tests',
  testIgnore: '**/design-history/**',
  fullyParallel: true,
  retries: process.env.CI ? 2 : 0,
  reporter: [['html', { open: 'never' }], ['list']],
  use: {
    baseURL: 'http://127.0.0.1:4173',
    trace: 'on-first-retry',
    screenshot: 'only-on-failure',
  },
  projects: [
    {
      name: 'mobile-chrome',
      use: { ...devices['Pixel 7'], deviceScaleFactor: 1 },
    },
    {
      name: 'desktop-chrome',
      use: {
        ...devices['Desktop Chrome'],
        viewport: { width: 1280, height: 800 },
        deviceScaleFactor: 1,
      },
    },
  ],
  webServer: {
    command: 'npm run dev -- --host 127.0.0.1 --port 4173',
    url: 'http://127.0.0.1:4173',
    reuseExistingServer: !process.env.CI,
    env: { PLAYWRIGHT: 'true' },
  },
  expect: {
    toHaveScreenshot: {
      maxDiffPixelRatio: 0.01,
      animations: 'disabled',
    },
  },
})

9Risks & edge cases

  • Seed migration: insert only missing slugs. Never wipe or overwrite existing game rows, sessions, or players.
  • Open-mode completion: total_rounds: 0 must not make the scoreboard empty. Use rounds.length in the max-rounds calculation.
  • Trailing unscored round: Finish deletes it; Undo relies on the last scored round becoming unscored again. Verify both directions.
  • Winner direction: remove the Pay Me slug check so Low Score behaves identically.
  • Dealer leakage: generic games should not show a dealer. Gate assignment on usesDealer.
  • Up & Down rules: the hook rule and “not everyone can succeed” checks remain in submitRound for now. They only apply to that slug, so generic games are unaffected.
  • Long games: open-ended sessions can accumulate many rounds. The one-query scoreboard load and wrapped history grid keep the UI usable.
  • Empty points: currently interpreted as 0. If that feels risky during testing, add explicit “required” validation for the points field.
  • Visual snapshot flakiness: generate baselines on Linux, pin the Playwright version, disable animations, use a small maxDiffPixelRatio, and keep dynamic content (dates, live timers) out of the captured screens. If a snapshot fails, inspect the expected/actual/diff images in the HTML report before updating.
  • Design-history repo size: capture only the key screens, use JPEG quality ~85, and run the capture manually at milestones. Baselines and gallery images are committed; test reports and traces are not.
  • CI runtime: Playwright adds browser install and test time. Start with Chromium only and two projects; add WebKit/Firefox later only if a real device issue demands it.

10Visual iteration notes

Once we switch to build mode, these are the things worth trying on a real phone before locking the design:

  • Card density: decided — one card per row at every screen size. The list is width-capped on desktop rather than switching to multiple columns.
  • Leader treatment: subtle “Leading” pill vs. no in-progress highlight. The mockups show the pill; it can be removed if it feels noisy.
  • History expansion: per-card toggle (shown) vs. a single global “Show all rounds” control. Per-card keeps the screen short.
  • Submit dock: sticky bottom bar vs. a normal button at the end. Sticky is better for 6+ players but takes vertical space.
  • Finish placement: round-bar action (shown) vs. a secondary button in the submit dock. Round bar keeps the primary action singular.
  • Recent rounds: last two (shown) vs. last three. Two keeps cards compact; three gives more context.
  • Completed screen: banner + cards (shown) vs. a dedicated final leaderboard sorted by rank. A sorted leaderboard may be a nicer end state.
  • Points input: plain number input vs. number input with quick +/- steppers for common values.
